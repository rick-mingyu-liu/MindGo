# TermPocket conversational financial agent design

Date: 2026-10-14. Status: proposed design for review; isolated runtime probe passed essential behaviors with adapter caveats.
Base: origin/main dabafaa. No open PRs at inspection. Existing DeepSeek and stale mobile worktrees are not modified. The user subsequently authorized retiring stock/watchlist and one-shot planning on the separate chore/retire-legacy-planning-stocks branch, which carries this design/probe. That retirement is a prerequisite change; the agent described here remains proposed.

## Intent and delivery gates

Canadian university/college students can record actual spending, investigate records, and prepare savings goals and study/co-op/summer plans through persistent English, Chinese or mixed-language text conversations. Typing remains a permanent first-class interaction. Voice capture, transcription, speech and continuous voice are excluded. Dashboard, goals, imports, and manual transaction creation/editing remain available.

Deliver in three reviewable phases: (1) runtime acceptance probe and storage/write-safety foundations; (2) integrated recording, investigation, conversations and approved memory; (3) deterministic goals/term planning, primary entry-point transition and complete acceptance verification. Foundations do not count as a working agent. The user authorized removing the legacy entry point ahead of agent implementation. Add the new agent entry point only when its core workflows pass; do not advertise a placeholder agent. Each phase receives independent review, focused commits, a PR against main and passing CI; never merge/deploy or touch production databases.

## Runtime decision

Recommended: Claude Agent SDK with DeepSeek's official Anthropic-compatible endpoint. The isolated probe passed real tool roundtrips, native continuation, restrictions, cancellation, error/timeout and usage checks (SDK 0.3.300 / Claude Code 2.1.300); see ../probes/2026-10-14-agent-runtime/REPORT.md. Adoption still requires application tests and written-design review. The existing OpenAI chat-completion success is insufficient. Keep the runtime behind `backend/services/agent/runtime.ts`; the application consumes its own progress/text/tool-result/completed/failed/cancelled events, never SDK events.

Two alternatives: a bounded DeepSeek native tool-calling loop behind the same interface (smallest fallback if SDK continuation/tool restrictions are incompatible), or another provider (changes cost/privacy and is not authorized). Neither alternative is selected automatically. Record precise probe results before recommending a change.

Probe fictional data only: custom in-process MCP tool/result round trip, two calls in one turn, continuation, denied builtin and nonallowlisted tools, cancellation, provider rejection, deadline, and usage fields. Disable builtin tools, persistence, project settings, filesystem context and ambient Claude credentials. Keep credentials/transcripts out of reports. Use persistSession:false and bounded database transcript replay for the application; native SDK resume was verified separately but creates a second disk transcript. Probe token counts are available; USD estimates have unknown price basis and must not be shown as DeepSeek billing. Check result.is_error even when subtype says success; enforce tool count in handlers because maxTurns permits parallel calls. Application-level replay/account-isolation acceptance remains in phase 2; do not maintain an undeletable second transcript store.

An AgentRuntime accepts a server-built context (user identity held outside model inputs, owned conversation, currency/timezone/language, bounded history and approved facts), input, allowlisted tool handlers and AbortSignal. It returns normalized events and minimal token/latency/termination metadata. No shell, arbitrary SQL, filesystem or unrestricted network tools. Each tool handler closes over server identity and verifies ownership. Untrusted descriptions, imported text, history and memories are data, not instructions. No database transaction remains open during model work.

Initial budgets: one active run/user, four active runs/process, 20 turns/user/hour, 90 seconds/turn, 8 tool calls/turn, 4,000 input characters, 16,000 tool-output characters/turn and 4,000 output tokens. Context: newest 30 messages up to 24,000 characters, one summary up to 4,000 characters, at most 30 applicable approved facts. Reject excess with stable localized codes. Persist run admission/usage per user so limits survive restart. Admission locks the owned preference row on a dedicated database client, expires stale leases, counts the hourly budget and inserts a new lease atomically; a partial unique index on user_id for active status is the final single-run guard. Global process concurrency is bounded independently; active run leases expire at the hard deadline. No recurring agent loop or database polling. HTTP progress streams and explicit cancel/retry use run ids and idempotency keys. Disconnection cancels execution; completed messages/drafts remain retrievable. Cancellation is carried by closing the run's streaming connection, which aborts the runtime on its owning instance; an explicit cancel endpoint also persists revocation. Lease/revocation checks precede every tool and final write. Deployment requires proxies that propagate stream disconnects. If a disconnect is lost, provider execution may continue until the 90-second deadline, but revoked/deleted contexts cannot write. The UI reports cancelling until the owner acknowledges or the deadline expires.

## Reuse and targeted corrections

`moneyFacts.ts` owns existing SQL totals, half-open windows and term pace; generalize its internal aggregate to explicit report currency/date windows/timezone, preserving the public MCP's existing three totals-only tools. Add internal bounded transaction detail and category/date investigation with explicit truncation and record ids. Do not expose them over external `/mcp`.

The retired `aiController.getUserFinancialData` summed mixed currencies and labeled goal progress as savings; do not restore that calculation path. Keep exchange conversion in `exchangeRateService.ts`, adding bounded timeout, finite/positive rate validation and rate/as-of/source metadata. Never silently use 1 for a failed cross-currency conversion. Reports disclose current-rate conversion rather than historical rates. Financial arithmetic is deterministic backend decimal/minor-unit code with explicit rounding; prompts explain computed outputs only. Existing canonical categories remain canonical strings; English/Chinese aliases map to these identifiers. Groceries/买菜 maps to Groceries, restaurant meals/餐饮/吃饭 to Dining Out; unclear category asks or uses a visible editable suggestion.

Reuse the import validators and review-table patterns; its direct client-payload endpoint is not the agent authorization model. Add shared validators rather than reproducing permissive manual-route validation. Agent transactions use a new `agent` source value after a read-only source audit; update schema/types/migration together. Existing manual editing remains authorized through existing forms.

## Data handling decision

The user chose not to add automatic masking of financial inputs sent to the agent. Retrieve and send only relevant data, retain existing credential/log protections, and disclose provider processing and administrator access. Do not claim anonymity or end-to-end encryption. Redaction used to honor deleted memories is a separate deletion control and still applies.

## Account context and bilingual behavior

Add owned server preferences: reporting currency (CAD default), IANA timezone (America/Toronto default, explicitly displayed and editable), reply preference (auto/en/zh). UI defaults English. Preserve explicit existing browser language choices; migrate browser currency only after authenticated review to prevent a shared-device preference becoming another user's setting. Browser locale/timezone may suggest choices, never silently overwrite account settings.

Auto replies follow the current input language; mixed input follows its dominant conversational language, asking only when needed. A fixed preference overrides auto. All controls, progress, failures, validation and deletion explanations have en/zh translations. Relative dates use the account timezone and a server clock; draft cards show interpreted YYYY-MM-DD dates and visible currency defaults. Chinese input alone never means CNY. Unsupported/ambiguous dollars, amounts, dates or planned-vs-recorded events require clarification. CAD default is allowed when no conflicting currency evidence exists and is shown before confirmation.

## Transaction drafts and confirmation

Model tool `propose_transactions` validates actual-event candidates and creates draft versions only. Hypothetical/future affordability questions invoke scenario tools, never transaction proposals. Examples include one English expense, two Chinese expenses and mixed-language batches. A conversational yes/okay/好的 cannot authorize execution: no confirmation tool is exposed to the model.

Draft payload has immutable row ids, type, decimal amount string, supported currency, canonical category, description <=255 characters, actual date and interpretation/default annotations. Max 50 rows/batch. Positive decimal amounts have at most 2 fractional digits and fit DECIMAL(10,2). All rows can be edited in cards or through follow-up proposals. Revisions atomically increment version and invalidate the previously reviewed version. A pending ambiguity produces questions, not invented payloads.

Confirm endpoint accepts draft id, reviewed version, selected row ids and an idempotency key; the server reads its stored payload, never a replacement financial payload. Lock owned draft on a dedicated client, validate version/status/expiry and ownership, revalidate values and goal state, insert selected transactions atomically, record receipt and commit. Only then show success. Idempotency keys bind to a server fingerprint of action id, reviewed version and sorted selected row ids. Under lock, look up the receipt before stale-version validation: exact retries return the same committed ids; reused keys with different fingerprints return conflict. Unique draft-row execution keys and confirmation receipts make concurrent clicks/retries return the same committed ids. Selected confirmation creates a new reviewed version for remaining rows; clients must reload before another confirmation. Stale requests return version conflict. A lost HTTP response can be recovered by receipt lookup.

Drafts expire after 24 hours, enforced at read/confirm time and unconfirmed actions removed in the existing hourly maintenance sweep. Executed actions/versions retain payload-free tombstones for receipt foreign keys and deduplication; scrub their payloads after undo expiry. Cancelled, expired, failed and superseded states are visible. Newly inserted agent entries have a 10-minute undo receipt: lock receipt, delete only the exact owned created rows whose updated_at still matches receipt snapshots, and mark undone atomically. If a row was manually changed, reject the whole undo with explicit conflict. Undo is idempotent; no arbitrary edit/bulk delete/transfer/investment tool exists.

## Investigation and planning

Internal read tools: `financial_summary(start,end_exclusive,currency)`, `transaction_details(start,end_exclusive,category,cursor,limit<=50)`, `goals`, `approved_facts`, and `calculate_scenario(validated assumptions)`. Query windows limited to 5 years; paginate capped detail. Use term helpers for study-term comparisons. Responses attach exact windows, currencies, current conversion assumptions, relevant categories/record references, coverage and missing-data limits. Compare equal elapsed windows for a current term; distinguish full-term comparisons. Fetch current figures every time.

Scenario inputs distinguish user-reported cash with an as-of date, expected income events, fixed expenses, tuition, reserve, goal allocations and simulated purchases, each with currency/date/provenance. Ask for missing cash/income/tuition rather than treating net recorded flow as a bank balance. Goal progress is neither cash nor an extra expense. Avoid counting one expense twice when already recorded; scenarios show which items are future-only. Compute event-based cash projections over explicit dates, minimum projected cash, reserve gap and contributions needed by deadline. Preserve immutable assumptions and rate snapshot alongside result. Unknowns stay unknown; a plan can show incomplete assumptions but cannot claim affordability.

Use savings_goals as authoritative targets/progress. `propose_goal` previews validated creation or explicitly selected goal update; updates include expected updated_at and fail on concurrent manual changes. No automatic goal selection by name. `propose_plan` stores only dated scenario assumptions/results, term context and owned goal references that savings_goals cannot express. Plan revisions use the same versioned confirmation protocol. Later retrieval loads current goal records; a snapshot is labeled historical. Deleting a referenced goal leaves an explicit missing-goal state, never recreates it from memory. No stock ticker recommendations.

## Storage, ownership and migration

New records use NOT NULL user_id, TIMESTAMPTZ UTC instants and DATE calendar days. Every owned parent exposes UNIQUE(id,user_id); child references include user_id so a valid id cannot associate another user's data. Source-message references also include conversation_id, enforced through a UNIQUE(id,conversation_id,user_id) parent key, so even two conversations owned by one user cannot be incorrectly associated. Model-supplied user_id is rejected/ignored at every boundary. Return indistinguishable 404 for nonexistent and other-user resources.

Tables:
- agent_preferences: user_id PK/FK, currency CHECK, timezone validated in API, reply preference CHECK, updated_at.
- agent_conversations: id UUID, user_id, title (non-sensitive default), summary bounded TEXT, summary_through_message_id, created/updated_at. Summary belongs to the conversation only.
- agent_messages: id UUID, user_id, conversation_id composite FK, ordered sequence UNIQUE(conversation_id,sequence), role/status CHECK, content bounded TEXT, created_at. Messages have client request keys for retry dedupe.
- agent_runs: id UUID, owned conversation, request key, status/lease timestamps, usage counters and terminal error code, no raw tool bodies. Per-user/time index supports bounded usage admission.
- agent_facts: id UUID, user_id, optional source conversation/message composite references, kind CHECK (reserve, recurring_expense, expected_income, term_context), validated structured payload, approval state, version, valid_from/to, created/updated_at. Pending proposals live in drafts; approved facts only enter retrieval. Facts never store current balances or duplicate goals.
- agent_actions: id UUID, owned conversation/message (nullable after conversation deletion for executed tombstones), kind CHECK, current version/status/expiry, created/updated_at. agent_action_versions stores immutable validated payloads with composite ownership references and UNIQUE(action_id,version).
- agent_action_receipts: owned action/version, idempotency key UNIQUE(user_id,key), selected row ids/result ids, execution state and undo expiry. agent_created_transactions records owned inserted ids and timestamp snapshots, ensuring each action row executes once.
- agent_plans: id UUID, user_id, name, explicit window/currency, assumptions/result JSONB, version, created/updated_at. agent_plan_goals associates only owned plans and owned existing goals, with nullable live goal_id and a historical goal-id/name snapshot; owned goal deletion clears the live link while retaining an explicit missing-goal marker. Legacy goals need a non-destructive UNIQUE(id,user_id) index for composite references; no NOT NULL tightening of legacy rows.

JSONB has discriminator/size checks plus strict application validation; it is not an unconstrained memory dump. Index conversation lists by (user_id,updated_at DESC), messages by (user_id,conversation_id,sequence), facts by (user_id,kind,approval_state,valid_to), actions by (user_id,conversation_id,status), runs by (user_id,created_at). Composite nullable provenance uses ON DELETE SET NULL for source columns only; ownership remains NOT NULL. Test PostgreSQL version support for column-specific SET NULL or use explicit deletion updates.

Reserve the next available numbered migration only after refetching main. Add new tables/indexes/preferences and agent source; no deletion/rewriting of incompatible existing rows. Audit legacy source/currency/amount/ownership before any tightened constraints, report incompatible rows by counts only. Keep numbered SQL, schema.sql and types/db.ts synchronized. Existing migration process uses recorded SQL with psql -v ON_ERROR_STOP=1; test fresh schema twice and upgrade from pre-agent schema on disposable PostgreSQL databases, including existing fictional data and rollback on failure. Never use DATABASE_URL from .env for tests/migrations.

## Memory, deletion and retention

Conversation history persists until user deletion; no 30-minute ai_plans policy applies. Bounded summaries are conversation-local, regenerated only from existing messages and never treated as approved facts. Approved durable facts require inline preview + explicit Remember/Update button, with structured amount/date/currency and provenance. Corrections create a versioned proposal, not overwrite by casual remark; expired facts are excluded at read time and shown as expired in controls. Delete facts physically; cancel active runs and increment the conversation/context epoch. Invalidate summaries and redact the original fact proposal/approval and affected message spans from future runtime retrieval (retain their UI history with a deleted-memory label). A bounded owned suppression marker stores source message ids/span offsets and the former fact id only, never its deleted value. Summary regeneration uses that redacted view; deletion tests ensure casual history and cached run contexts cannot repropose the fact automatically. An explicit new user request can propose remembering a fact again, requiring a fresh confirmation.

Delete conversation atomically removes messages, summary, unconfirmed drafts and conversational run context. Separately approved facts survive with source references cleared and UI explicitly says they survive; user may choose also delete the listed sourced facts in the same transaction. Saved transactions/goals/plans and minimal confirmation/undo receipts survive; detach conversational provenance on executed action/version tombstones without retaining message text or draft financial payload. Receipt transaction snapshots contain only the ids/timestamps needed for remaining undo. Tell the user exactly which records remain. Cancel active runs before deletion and forbid writes after the deletion/version epoch; no opaque SDK resume/session file survives deletion. Every new run retrieves current approved facts. Deleted facts cannot reappear from summaries, caches or replayed SDK sessions.

Operational run metadata retains 30 days, swept hourly; unconfirmed payloads expire in 24 hours. Financial receipts retain only dedupe/audit ids after undo expiry, with payloads cleared. Settings clear-all must explicitly offer conversations, approved facts and plans alongside financial records; per-category deletion counts/confirmation text match the selected scope, and account deletion cascades all owned agent stores. Plans and approved facts remain until deleted or account deletion. The existing ai_plans table/read-time expiry/hourly cleanup stays during transition; no migration drops it. Legacy planning generation endpoints already return a deliberate retirement response following the separately authorized retirement; history remains readable until its original expiry. Stock-provider operations are retired too; only archived watchlist clearing remains for data deletion.

English default, both locales, light/dark, 375px phone and 1440px desktop verified with fictional authenticated data. Keyboard focus, accessible card field labels, stream announcements and cancel state are required. No microphone UI.
