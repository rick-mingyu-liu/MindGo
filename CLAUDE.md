# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

TermPocket (the repo and its infrastructure — Vercel, Render, Neon, the `mindgo` database names — are still named MindGo) is a personal finance app: an Express/PostgreSQL REST API (`backend/`), and a Next.js/TypeScript frontend (`frontend/`). The two are separate npm projects with independent `package.json` files — run commands from within the relevant subdirectory. They are deliberately *not* npm workspaces: workspaces consolidate every lockfile at the repo root, which breaks `npm ci` for both deploys, since Render builds with root directory `backend` and Vercel with `frontend`.

## Commands

### Backend (`cd backend`)
```bash
npm install            # also builds: `prepare` runs tsc into dist/
npm run build          # clears dist/, then tsc → dist/ (CommonJS). Source is TypeScript: docs/superpowers/specs/2026-09-17-backend-typescript-design.md
npm run dev            # tsx watch app.ts (plain node cannot require the .ts modules)
npm start              # node dist/app.js (production — the compiled output, which is .js)
npm run db:setup       # create schema from db/schema.sql (idempotent, CREATE IF NOT EXISTS)
npm run db:seed        # (re)seed the demo account (john.doe@example.com / password123)
backend/scripts/rehearse-linux.sh [--live]  # from the repo root, with docker-compose.test.yml up: Render's npm ci + build + preflight in a fresh node:<.node-version> Linux container
npm run agent:eval     # opt-in paid Pocky evaluation: 37 fictional cases, real runtime/DeepSeek, in-memory records (no DB); README "Evaluating Pocky"
npm run agent:preflight  # read-only Pocky deploy check (config, DB/migrations 013-015, SDK binary, DeepSeek reachability); `-- --live` adds one fictional model turn. Runbook: README "Deploying Pocky to production"
npm run lint           # eslint . (eslint 9, flat config in eslint.config.mjs; TypeScript only, via typescript-eslint)
npm test               # builds, then node --test 'dist/test/**/*.test.js' — unit tests always run; see below for the integration suite
```

## Tests

`backend/test/` holds the only automated tests. `npm test` builds the backend, then runs the compiled tests via `node --test` — no test framework is installed, and none is needed.

asserts the unverified-account retention predicate, its reclaim twin, and that errors propagate), `schedulerService.test.ts` (the interval plumbing via `mock.timers`, the hourly maintenance job — no query before the first hour, the account cleanup once per run, it and agent housekeeping not stopping each other when one fails, no overlap, no replay, `stop()` cancelling — and the weekly report's next run on a UTC clock), `expiryAtReadTime.test.ts` (an expired verification token is refused, whether or not the sweep has run), `registerReclaim.test.ts` (registering over a stale unverified account replaces it; asserts nothing logged contains screenshot text or row values, even when the database throws). `test/helpers/ocrLayouts.ts` is not a test file and is not run — `npm test`'s `dist/test/**/*.test.js` glob does not match it.

  **`sharedContracts.test.ts` checks that every category the frontend's picker offers has an explicit colour in `CATEGORY_COLORS`.** Like `demoData.test.ts`, it reads files outside `backend/`, so it fails on a checkout without `frontend/`. (It also pinned the copies in a React Native client, `mobile/`, until that client was removed.)

  `agentPreflight.test.ts` covers `scripts/agentPreflight.ts`'s pure parts: no secret (fake key, DB URL, password, host) survives formatting, the exit code follows FAIL alone, 013/014/015 PASS/WARN/FAIL from stubbed catalog facts, and that gathering facts issues only `SELECT`s.

  `agentEval.test.ts` covers the fictional evaluation harness: scoring and numeric boundaries, strict fixture SQL/ownership/cursors/FX/goal versions, real-tool totals, CLI validation and pass thresholds, blocked pool access and restoration, bounded key-redacted output. `npm run agent:eval` is opt-in and paid; it never runs in CI and never opens a database. Cases, defaults and fixture data live under `backend/eval/`; keep them fictional. Required tools must succeed; excluded tools include failed handler calls. The harness cannot observe SDK schema-rejected tool names.

  One trap in `schedulerService.test.ts`: `mock.timers`' fake `Timeout` **ignores `unref()`** — `hasRef()` stays `true` however you call it — so the one test that checks the timer does not hold the event loop open has to run on a real timer, in its own `describe`.
- **`api.test.ts` needs a database and skips without one.** It refuses to borrow `DATABASE_URL` from `.env`; point it at a throwaway database instead:

  ```bash
  docker compose -f docker-compose.test.yml up -d --wait   # PostgreSQL 17 like CI, in memory, local only, no password
  export TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:55432/termpocket_test
  npm run build && DATABASE_URL=$TEST_DATABASE_URL npm run db:setup && npm test
  ```

  Any PostgreSQL 15+ works (migration 013 needs 15; Homebrew's default may be older). The compose server has SSL on with a self-signed certificate, because under `NODE_ENV=production` the backend always connects with SSL.

  The database must already have the schema (`npm run db:setup`). `db:setup` never drops tables, so a test database created before migration 014 also needs 014 applied, or `api.test.ts`'s removed-table check fails. The suite creates and deletes users, which is why opting in is deliberate — never point it at production.

  It raises `RATE_LIMIT_AUTH_MAX` for itself. `authLimiter` allows 5 requests per 15 minutes per IP across `/register`, `/login`, `/resend-verification` and `/test-email` **combined**, and a suite that touches both login and register trips that almost immediately.

**Additional MCP coverage:** `moneyFacts.test.ts` exercises pace windows, early-term spending, future-dated rows, zero baselines, clamping, leap years and timezone boundaries. `accessTokenRoutes.test.ts` covers JWT ownership, one-time secrets, validation, safe logs, transaction locking, revocation and the per-user mutation budget. The database-backed `api.test.ts` checks concurrent token creation through both the API and the shared service.

The frontend has no tests. Verify UI changes by running the app.

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs lint plus tests for the backend against a Postgres service container, and `check:locales`, lint and `build` for the frontend. It uses `npm ci`, so a `package.json` that disagrees with its lockfile fails the build rather than resolving to whatever the registry serves.

## Backend architecture

Request flow: **route → (auth middleware) → validation → controller → service/db**. [backend/ARCHITECTURE.md](backend/ARCHITECTURE.md) has the diagram, the patterns in use, and where the layering still leaks.

- **TypeScript**, compiled to **CommonJS in `dist/`** by `tsc` (`module: nodenext`, no `"type": "module"` in `package.json`). `dist/` is gitignored and is what `npm start`, `npm test` and `db:setup` run; `npm run dev` runs the source through `tsx`. Conventions, all of which the conversion preserved deliberately (spec §4.1):
  - **Export shape is the CommonJS one.** A module that was `module.exports = <single value>` is `export = value` — every router and controller, `config`, `logger`, `errorHandler`, `auth`, and the service singletons — and is imported with `import x = require('./x')`, not `import x from`. A module that was `module.exports = { a, b }` uses named exports and an ordinary `import { a } from './x'`. **`export default` is used nowhere**, and changing an export shape is out of scope.
  - **[backend/types/](backend/types/) holds the shared types**: [types/db.ts](backend/types/db.ts) (one interface per table — see the Database section; it is edited with `schema.sql` and every migration), [types/express.d.ts](backend/types/express.d.ts) (merges `AuthUser` into Express's own `Request`, which is why a controller reads `req.user.userId` with no cast), and [types/import.ts](backend/types/import.ts) (the screenshot parser's vocabulary).
  - **Row types are named at the call site**: `query<TransactionRow>(sql, params)`. `query()` is generic but cannot infer a shape from a SQL string, so an unparameterised call gives you `QueryResultRow` and nothing useful.
  - **On the import, MCP, access-token and agent paths, a caught error reaches a log only through `errorSummary(e)`** ([backend/utils/errorSummary.ts](backend/utils/errorSummary.ts)), which yields `{ error, code }` and never the message — a pg error's message can quote the row that failed. It is the shared form of the `{ userId, error, code }` objects these endpoints log (MCP tool errors also include the tool name). **Everywhere else a caught error is still passed whole** to `console.error`/`logger.error` — about 57 sites — and `logger.error` prints its stack, message included. So this is a rule those paths keep, not an invariant the backend has: elsewhere, error messages still reach logs.
  - **Anything reading a file that is not code** — `schema.sql`, test fixtures, `eval/` — resolves from `packageRoot(__dirname)` ([backend/utils/packageRoot.ts](backend/utils/packageRoot.ts)). A path built from `__dirname` alone points into `dist/` once compiled, where those files were never copied.
  - **No `any`.** `@typescript-eslint/no-explicit-any` is an error and there are no `eslint-disable`s for it. `strict`, `noUncheckedIndexedAccess`, `noUnusedLocals` and `noUnusedParameters` are all on.
- [backend/app.ts](backend/app.ts) wires helmet, morgan, cors, JSON parsing, mounts routers under `/auth`, `/transactions`, `/summary`, `/goals`, `/import`, `/access-tokens`, `/mcp`, `/agent`, then global error + 404 handlers. On startup it also calls `schedulerService.init()`.
- **All config is centralized** in [backend/config/index.ts](backend/config/index.ts) — ports, JWT settings, cron schedules, data-retention windows, validation limits, and API keys. Read env vars from here, not `process.env` directly, when adding features.
- **Auth**: [backend/middleware/auth.ts](backend/middleware/auth.ts) verifies the `Authorization: Bearer <token>` JWT and sets `req.user`. Protected routers apply it globally with `router.use(auth)` at the top of the route file (see [backend/routes/transactions.ts](backend/routes/transactions.ts)). Controllers read the user id as **`req.user.userId`**.
- **Validation**: use `express-validator` `body([...])` arrays in the route file, then check `validationResult(req)` at the top of the controller method. Query parameters take `query([...])` the same way — only `DELETE /transactions/auto-delete` does so far, and only because it deletes rows.
- **Terms**: [backend/utils/terms.ts](backend/utils/terms.ts) is the single definition of the Waterloo term calendar (Winter Jan–Apr, Spring May–Aug, Fall Sep–Dec). `GET /summary/rolling` takes **exactly one** of `?term=2026-spring|current|previous`, `?year=2026|current|previous`, or `?months=N` — passing more than one is a 400 — and echoes `term`, `year`, `periodLabel`, `termLabel`, `startDate`, `endDate` so a client never computes a date or a name. **A year is three terms**, not twelve rolling months: the terms tile Jan–Dec exactly, so `?year=2026` shares its boundaries with Winter/Spring/Fall 2026 and its totals are always their sum. The dashboard's period selector (This term / Last term / This year / Last year) defaults to `term=current`. Anything needing term boundaries — the summary views, and the retention job when it lands — must go through it rather than computing its own, because a view and a deletion that disagree about where a term starts would fail silently. Bounds are half-open `[start, end)`, matching the `date >= $1 AND date < $2` queries. **Do not build dates with `new Date(y, m, d).toISOString()`** anywhere: it is off by a day east of UTC. All known instances are gone (items 21 and 23); use integer arithmetic, or `toDay()` from `utils/dates.ts` when starting from a `Date`.
- **Address validation at registration**: [backend/services/emailValidationService.ts](backend/services/emailValidationService.ts) exports one function, `validateEmail(email)` → `{ valid, reason?, source }`. MailboxLayer where `MAILBOXLAYER_API_KEY` is set, its own 30-domain disposable list otherwise. **It never throws and never blocks on its own failure** — no key, a network error, an HTTP error, an apilayer error payload (HTTP 200 with `success: false`) or an unrecognised response shape all fall back to the domain list, loudly via `console.error`. The previous version turned each of those into a rejected or 500ing registration. Keep that property if you touch it: `test/emailValidation.test.ts` has a case per failure mode.
- **Log levels**: [backend/utils/logger.ts](backend/utils/logger.ts). `info`, `warn` and `debug` are gated on `config.logging.enableConsoleLogs` = `NODE_ENV === 'development'`, so **they print nothing in production**. `error` and `audit` always print. Use `logger.audit` only for events that destroy or irreversibly change user data — the retention deletions do, which is why they moved off `info`. `LOG_LEVEL` is close to inert: it gates `debug()` and nothing else.
- **Logging user data**: **never log a credential** — verification tokens, JWTs, password hashes. For addresses, the rule is *log a user id where one exists, and a masked address only where one does not* (before the INSERT, or when a lookup found nothing). `maskEmail()` in [backend/utils/privacy.ts](backend/utils/privacy.ts) produces `j***@example.com`. Registration leaked verification tokens this way once; `test/registerLogging.test.ts` guards it by running the real handler and inspecting everything it printed.
- **Zone-less timestamps are UTC**: `users`, `transactions`, `savings_goals`, `import_batches` and `access_tokens` use `TIMESTAMP` without a zone. `db/connection.ts` runs every session in UTC (`SET TIME ZONE 'UTC'` next to `search_path`), parses `TIMESTAMP` as UTC and writes `Date` parameters as UTC (`parseInputDatesAsUTC`). Before that, both directions were right only when the Node process also ran in UTC: on a Toronto-time machine an email verification link expired four hours late. `test/dates.test.ts` pins the parser across four timezones.
- **Dates are days, not instants**: `db/connection.ts` registers a `pg` type parser so a `DATE` column arrives as the plain string `'2026-08-28'`. Without it node-pg builds a `Date` at the *server's* local midnight and `res.json()` re-serialises that in UTC, so one stored day left the server as a different string per host and every viewer west of it read the day before. Consequences worth keeping in mind: **never `new Date(day).getMonth()`** — a plain `'2026-08-01'` parses as UTC midnight and answers July west of UTC, which silently files a month of transactions under the month before. Use [backend/utils/dates.ts](backend/utils/dates.ts) (`toDay`, `monthOf`, `formatDay`, `monthSpan`) on the backend and [frontend/lib/date.ts](frontend/lib/date.ts) (`toDay`, `formatDay`, `formatDayRange`, `todayDay`, `daysUntil`) on the frontend. Both accept `'2026-08-28'` and `'2026-08-28T00:00:00.000Z'`, so a stale deploy of either side still renders the right day. The frontend copy has no test — the frontend has no runner — but the backend twin is covered by `test/dates.test.ts`.
- **DB access**: [backend/db/connection.ts](backend/db/connection.ts) exports `query(text, params)`. Notable pattern: the `pg` Pool is **lazily created and auto-closed after 5 minutes of inactivity** to save connections. Always use parameterized queries (`$1, $2, ...`); controllers build filtered queries by incrementing a `paramCount` (see `getTransactions`).
- **Multi-currency**: monetary rows store a `currency` column; conversion happens at read time via `services/exchangeRateService.ts`. Allowed currencies: `CAD, USD, EUR, GBP, AUD, CNY`.
- **Removed features**: the stock watchlist and one-shot AI Planning are gone, code and storage. The `/investments` and `/ai` routers and `POST /goals/from-ai-plan` are no longer mounted, so those paths get the global 404 (`removedFeatures.test.ts`). Migration `014_drop_watchlist_ai_plans.sql` drops the `watchlist` and `ai_plans` tables; **deploy the frontend, then the backend, then apply 014** — the previous frontend's clear-all calls the removed watchlist endpoint, and the previous backend queries `ai_plans` from its hourly sweep and `/ai/plans`, and would error on a database without it. Do not restore either feature. The only remnants are two frontend redirects in `next.config.js`: `/investments` → dashboard and `/ai-planning` → `/agent` (a separate recording flow, not restored one-shot planning), kept so old bookmarks land somewhere.
- **Scheduler** ([backend/services/schedulerService.ts](backend/services/schedulerService.ts)): weekly report emails via `node-cron`, plus one **hourly maintenance job** that deletes stale unverified accounts, plus agent housekeeping in the same run only when `config.agent.enabled` is true. It used to be two jobs, every 5 and 10 minutes, which left Neon (it suspends after about 5 idle minutes) almost no chance to scale to zero. Deletion is housekeeping, not enforcement: verify-email checks `email_verification_expires` itself, so an expired row behaves as gone until the sweep removes it, normally within the hour (longer after downtime, or never if the process never stays up for an hour). An unverified account is stale once it is older than 30 minutes *and* its verification link has expired, or older than 24 hours whatever its link says (`unverifiedAccountIsStale()`). The second condition means a resent link is never swept out from under its user; the cap means resending, which is unauthenticated, cannot keep someone else's registration of an address alive forever. Registering the address again replaces a stale row on the spot (`reclaimStaleUnverifiedAccount()`), so whether an address is free never depends on when the sweep last ran. **Do not** add a database query to `/health`, a keep-alive, or another short-interval job without weighing that against Neon's idle window. The deletions themselves live in [backend/services/cleanupService.ts](backend/services/cleanupService.ts) and **throw** on failure rather than logging and returning — the caller decides what a failed cleanup means. Nothing mounts them over HTTP; the scheduler is the only caller. The weekly report runs at 7 p.m. `config.cron.timezone` (America/Toronto), not host time — the host is UTC. **node-cron must stay at 4.6 or later**: 4.2 computed "next Sunday" as 2034-01-01 and slept until then, so the weekly email never went out. Add a new recurring job through `scheduleInterval(name, ms, task)`, which awaits the task, logs the row count when the task returns one (the maintenance job logs each cleanup itself), and `unref()`s the timer. It is a chain of timeouts: the first run is one interval after scheduling (never at startup), the next is armed only when the current one finishes (no overlap), and missed runs after downtime are not replayed; a bare `setInterval` with a synchronous `try`/`catch` around an async call silently reports success.
- **MCP (`POST /mcp`)**: [backend/routes/mcp.ts](backend/routes/mcp.ts) lets a personal agent read totals over JSON-RPC. It authenticates with a personal access token ([backend/services/accessTokens.ts](backend/services/accessTokens.ts): `mgo_` prefix, SHA-256 stored, revocable), **never the login JWT**, which can delete everything. Settings → AI connections manages tokens through the JWT-protected [backend/routes/accessTokens.ts](backend/routes/accessTokens.ts): `GET /access-tokens` lists metadata (including revoked tokens), `POST /access-tokens` accepts a trimmed 1–60-character name and returns the secret only in its `201`, and `DELETE /access-tokens/:id` revokes an owned active token. All responses use `Cache-Control: no-store`. Create and revoke share a per-user budget of 20 requests per 15 minutes (`RATE_LIMIT_ACCESS_TOKEN_MAX`); listing has only the general API limit. The CLI (`npm run access-token`) uses the same service. **At most five active tokens per user**, enforced on a dedicated connection with a transaction that locks the user row (`FOR NO KEY UPDATE`) before counting and inserting, so concurrent creates cannot exceed the limit. Its tools live in [backend/services/moneyFacts.ts](backend/services/moneyFacts.ts), aggregate in SQL, and must stay reads of totals: `test/mcp.test.ts` asserts every query is a `SELECT` (bar the token's `last_used_at`) and none reads `description` or `SELECT *`. Term boundaries come from `utils/terms.ts` like everything else. Current-term `pace` compares actual spending through today against the previous term's first equal number of days, clamps a shorter previous term, excludes future-dated rows and returns both half-open windows; a zero comparison baseline gives a null ratio and explanatory note.
- **Screenshot import**: OCR runs entirely in the browser ([frontend/lib/ocr/](frontend/lib/ocr/)) — the image never reaches the server. `POST /import/parse` ([backend/routes/import.ts](backend/routes/import.ts)) turns the OCR lines it receives into draft rows and stores nothing. `POST /transactions/import` writes the confirmed rows and one `import_batches` record in a single statement. `classify.ts` picks one of five layouts — `bank-list`, `receipt`, `uber-activity`, `uber-eats-orders`, `wechat-pay` — each parsed by its own module; the rules, and the measured gap thresholds behind them, are in the spec's §4 ([docs/superpowers/specs/2026-09-16-ocr-import-design.md](docs/superpowers/specs/2026-09-16-ocr-import-design.md)). A parser that sets `category` itself (including `null`) overrides the keyword guess. Fixtures copied from real screenshots keep the OCR boxes and replace personal details — keep it that way; real screenshots live only in the gitignored `eval/private/`. On a bank list an unsigned amount always carries `type_guessed`, because OCR drops minus signs with high confidence (a receipt or an Uber trip or order list fixes the direction by layout, so it does not; WeChat Pay prints its own + and −); the running-balance check verifies the amount only, never direction, for the same reason. **Never log OCR text, row values or request bodies** — errors are `{ userId, error: error.name, code: error.code }`, nothing more. The model is chosen by `eval/`'s benchmark and pinned in both [frontend/lib/ocr/profile.json](frontend/lib/ocr/profile.json) and [frontend/scripts/ocr-assets.js](frontend/scripts/ocr-assets.js) — change them together, then re-run the benchmark and `npm run fixtures` so the recorded backend fixtures match the new output.

### Conversation recording

The implemented `/agent` slice records actual income/spending in English, Chinese or mixed text, supports corrections to one editable pending batch, persists conversations across visits, answers plain-text questions about the user's own recorded income and spending through three read-only tools, and helps plan through deterministic projections and button-confirmed savings-goal proposals (Planning, below). There are no durable facts, conversation summaries, stored financial plans or voice input. Do not advertise those deferred features or restore retired stock/one-shot planning.

- [routes/agent.ts](backend/routes/agent.ts) owns orchestration and strict application JSON validation; every endpoint, including status, requires the login JWT. IDs from requests are always bound to `req.user.userId`. All responses are `no-store`; errors expose stable `agent_*` codes, never SDK/provider payloads.
- [services/agent/store.ts](backend/services/agent/store.ts) owns short database transactions, ownership locks, run admission, immutable draft revisions, confirmation and undo. Never keep a DB transaction open during model execution. Compound owner/conversation foreign keys defend associations too. [types.ts](backend/services/agent/types.ts) defines the application contract; [validation.ts](backend/services/agent/validation.ts) checks positive decimal strings, real calendar dates, the six currencies, and categories matching income/expense.
- [services/agent/runtime.ts](backend/services/agent/runtime.ts) lazily loads pinned Claude Agent SDK `0.3.300` with Zod `4.6.7` and DeepSeek `deepseek-flash`. It exposes `propose_transactions`, replacing the whole pending batch, three read tools (below) and four planning tools (Planning, below). It has no financial-write tool or DB access; the server-owned `assertActive` callback checks revocation before each invocation. Built-in tools/settings are disabled, unknown tools denied, and a hook counts attempts even when schema validation rejects them. **Thinking is disabled in the request body itself** (`CLAUDE_CODE_EXTRA_BODY={"thinking":{"type":"disabled"}}`): the SDK's `thinking:{type:'disabled'}` makes the CLI *omit* the field, and `deepseek-flash` reasons by default when it is absent — 4–9k hidden characters per round trip that count against the output-token and assistant-character budgets. That is what failed a production planning turn with `agent_limit_exceeded` after 31 s; do not drop the env var. When a limit trips, the runtime logs `Agent run hit a limit` with a `reason` (`tool_calls`, `tool_attempts`, `tool_output_chars`, `total_tokens`, `output_tokens`, `assistant_chars`, `final_chars`) and counts only, and the `AgentError` carries `usage` so `failTurn` records the failed run's tokens and executed tool calls (capped at 8, the column's check); the client still sees only the code. Spawn receives a closed environment allowlist and isolated temporary config/cwd; `persistSession:false` and cleanup prevent hidden SDK transcript storage. Never pass inherited credentials/configuration or log raw events. Only actual token counts are recorded; SDK dollar estimates are not authoritative DeepSeek billing.
- **Investigation** ([services/agent/investigation.ts](backend/services/agent/investigation.ts)): `spending_summary` (one window's income, spending, net and every category), `compare_spending` (two windows; differences are b − a, ratios b / a and null with a note when a is zero) and `transaction_details` (a page of rows, newest first, keyset-paginated on `(date, id)` with an opaque cursor bound to the window and filters). The route binds them to `req.user.userId` (`recordsFor`) and passes them in as `AgentInput.records`; the runtime never imports `db` and no tool argument names a user. Windows are half-open real calendar days, at most 1827 days; currency, category and type are validated against the agent's canonical lists; `limit` is 1–25 (default 15). Each row's description reaches the model only as `description_untrusted`: control characters and bidi overrides become spaces and it is clipped to 80 characters. Totals aggregate in SQL through `moneyFacts.groupedBetween` (shared with MCP, whose output is unchanged) and are summed in integer cents. Conversion uses current rates and says so in `conversion_note`; a missing, zero, negative or non-finite rate, or a provider that does not answer within 5 s, makes the tool answer `agent_rate_unavailable`, never a silent wrong number; `RateUnavailableError` keeps the cause's `code` (not its message) for `errorSummary`. Read calls share the eight-call and 16,000-character tool-output budgets with proposals, never touch the pending draft, and answer errors with a code only (`agent_invalid_input`, `agent_rate_unavailable`, `agent_records_unavailable`). A read result larger than the remaining budget is refused as `agent_output_budget` (narrow the window, filter, or summarise) without ending the turn; cumulative overflow still stops it with `agent_limit_exceeded`. The prompt envelope carries `context.calendar` — today, current and previous term, current-term-so-far and the previous term's same-elapsed window (`terms.sameElapsedWindows`, shared with MCP's pace) and the year — so the model never computes dates. **Descriptions, amounts, dates and categories of matching records go to DeepSeek**; the system prompt treats descriptions as third-party text never to be followed, forbids reading records from changing `pendingRows` unless the user's own current message describes a new transaction, requires every number to be quoted from a tool result with its window and currency, and requires plain text with no Markdown because the UI renders raw text.
- Only `POST /agent/conversations/:id/confirm` inserts transactions with `source='agent'`. It binds version, selected row IDs and request UUID; repeated matching requests return existing state. Chat text such as “yes” has no confirmation authority. Partial confirmation creates a new revision for remaining rows. Undo within ten minutes requires every saved transaction's exact PostgreSQL timestamp and tuple version to match; do not round timestamps through JavaScript `Date`.
- **Planning** ([scenario.ts](backend/services/agent/scenario.ts), [planning.ts](backend/services/agent/planning.ts), `spendingBaseline`/`listGoals` in investigation.ts): four more tools in the same `draft` server, under the same eight-call and 16,000-character budgets and the same `assertActive` check. `spending_baseline` averages income, expenses, net and each category over the last 1–12 (default 3) whole calendar months before the conversation's today, divided by the months with any record (like `moneyFacts.monthlyBaseline`), in cents through `groupedBetween`. `list_goals` returns at most 20 goals (target date nulls last, id) with named columns, `description_untrusted` cleaned and clipped like transaction descriptions, and `updated_at` as fixed-width microsecond text (`to_char(updated_at,'YYYY-MM-DD HH24:MI:SS.US')`, `GOAL_VERSION_SQL` in planning.ts, used by listing, proposing and confirming alike) — the version a proposal must quote. An amount that does not parse is an error (`agent_records_unavailable`), never a zero. `calculate_scenario` is a pure projection in integer cents over day strings (no `Date`): window `[start, end_exclusive)` ≤ 731 days, 1–40 events with weekly, `two_weeks` (biweekly pay: every 14 days, not twice a month) or month-end-clamped monthly repeats, ≤ 600 occurrences in the window, events in other currencies converted once per event at a listed current rate (`agent_rate_unavailable`, never a silent 1), end-of-day balances (the start day included, after its own events), lowest point, reserve shortfall and first breach, and goal math (`months_left` in whole calendar months, so `monthly_needed` is conservative and rounded up to the cent; a past deadline needs everything now). Without `starting_cash` it returns `status:'incomplete'`, `missing:['starting_cash']` and no balances; the prompt forbids affordability claims then. `propose_goal` validates one create or update, matching the goal form (create: no id, a target date that is required and not in the past; update: `goal_id` and `expected_updated_at` from `list_goals`, omitted optional fields keep their values, the target date cannot be cleared and a changed one may not be past, `current_amount` may exceed the target only if unchanged, a no-op is refused) and, for an update, reads the owned goal for a `before` snapshot; another user's goal is `agent_goal_not_found`, a stale version `agent_goal_conflict`. Its failures are repairable tool errors with fixed hints, not turn failures. A successful proposal travels in `AgentResult.goalProposal` and is stored only by `finishTurn`, after `active()`, so a cancelled or expired run cannot publish it; it supersedes the conversation's pending proposal. `ConversationState.goalProposal` is the conversation's most recent proposal (null if that one is superseded), with a pending one past `expires_at` reported as `expired` by the DB clock. Only `POST /agent/conversations/:id/goal-proposal/confirm` (`{proposalId, requestId}`) writes `savings_goals`: under `owned()`, exact replay returns state, a reused request ID for another proposal is `agent_request_conflict`, an active run `agent_busy`, a non-latest or decided proposal `agent_version_conflict`, an expired one `agent_expired`; a create whose target date is before today in the conversation's timezone (`(now() AT TIME ZONE timezone)::date`) commits `status='conflict'` and answers 409 `agent_goal_invalid`; an update locks the goal `WHERE id AND user_id` and compares `updated_at::text` exactly, otherwise it commits `status='conflict'` and answers `agent_goal_conflict` (a deleted goal too). `DELETE …/goal-proposal` (`{proposalId}`) cancels the pending one. Both need storage, not the provider key. Proposals expire after 24 hours; the hourly sweep stores that as `status='expired'` and deletes decided, expired and superseded proposals 30 days after `decided_at`, inside a savepoint so its failure cannot roll back the other cleanups. The scenario and goal values the model states go to DeepSeek like any other message content.
- Admission is one live run per user and 20 new turns per rolling hour in PostgreSQL; local process slots cap concurrent model requests at four. Storage caps users at 100 conversations and conversations at 200 messages. Runtime caps input at 4,000 characters, context at 30 messages / 24,000 characters, drafts at 12 rows, tool attempts/executions at eight, generated output at 4,000 tokens / 8,000 final characters, cumulative tokens at 32,000 and execution at 90 seconds. These limits live in `config.agent`. Context holds only `complete` messages, so cancelled or failed turns are never replayed to the model; truncation is not a summary. Run leases and `finishTurn` checks prevent late publication after cancellation/deletion.
- Conversation messages remain until deletion. Deleting a conversation cascades messages, drafts and runs but preserves financial transactions. Drafts expire 24 hours after the model proposal; edits and partial confirmation retain that deadline, and read/write checks enforce expiry independently of housekeeping. Draft expiry, the undo window and run leases are compared against PostgreSQL's `now()` in SQL, never the Node clock. The existing hourly sweep removes expired drafts, terminal runs/admission metadata older than 30 days, and minimal receipts after 30 days or after undo expiry if detached from deleted history. Receipts retain IDs, request hashes and exact row versions, not amounts/descriptions. Admission records survive history deletion so clearing conversations cannot reset the hourly budget.
- `AGENT_ENABLED=false` disables agent storage routes and maintenance before DB access; `/agent/status` returns `{available, storage}` (`storage` = the flag, `available` = flag and key) without querying storage. Set it true only after migration `013`. With storage enabled but no DeepSeek key, new model turns are refused with `agent_unavailable` (an exact `requestId` replay still returns saved state) while history, edits, confirmation, undo and deletion remain available. Keep these two states distinct in UI, tests and documentation.
- [frontend/pages/agent.tsx](frontend/pages/agent.tsx) owns recovery, cancellation, visible context, editable/selectable drafts and receipts. `/ai-planning` redirects there. [frontend/utils/agentApi.ts](frontend/utils/agentApi.ts) uses application-owned types and caller-owned errors. There is no polling; refresh/retry use server state and stable request IDs. Never enable confirm while edits are unsaved or a run is pending. Settings clear-all includes conversation deletion; it skips that step when `/agent/status` reports storage disabled, and reports partial cleanup only if deletion is refused as unavailable.
- The conversation screen's notice says only that conversations are stored and may be accessed by authorized administrators; by the owner's decision it does not name DeepSeek, which appears in Open Source Acknowledgements instead. Messages, relevant history, pending entries and date/currency/timezone context still go to DeepSeek. Do not claim end-to-end encryption or promise provider-side deletion when local history is removed.

`agentValidation`, `agentRuntime`, `agentInvestigation`, `agentScenario`, `agentPlanning`, `agentGoalProposalsOptional` (store behaviour without migration 015, and the cleanup savepoint, on a faked pool), `agentRoutes` and `agentMaintenance` tests run without a database/provider. `agentStore`, `agentInvestigationDb`, `agentGoalProposals` (confirm once, replay, concurrent confirms with the same and different request IDs, stale/deleted/foreign goals, a create date passed in the conversation's timezone, superseding, stored expiry after the sweep, cascade), `agentMigration` and `goalProposalMigration` (015 twice on main's schema with rows and twice on a fresh one, matching `schema.sql`; refuses a database without 013) tests (and `dropWatchlistMigration`, which applies 014 twice to a schema that has both tables with rows and twice to a fresh one, asserting counts-only notices and every other table untouched) require explicit `TEST_DATABASE_URL`, isolate fictional records/schemas, and must never use the `.env` database. The migration tests apply fresh/upgrade DDL twice and verify incompatible legacy source values abort without rewriting rows. Real provider acceptance is opt-in and uses fictional content only.

### Database

**Demo data is generated, not hardcoded.** [backend/db/demoData.ts](backend/db/demoData.ts) builds the demo account relative to `new Date()` — five terms of a Waterloo co-op student, alternating study and work terms, with the current term truncated at today. It exists because the old `seed.sql` hardcoded dates in 2025, so by August 2026 the demo's default window (`?term=current`) was empty and all three savings goals showed as overdue. Amounts are jittered by a seeded generator keyed on term and category, so the same day always produces identical data. `db:seed` **replaces** the demo user's rows inside one transaction using a dedicated client (`db.getPool().connect()` — `db.query` would put `BEGIN` and `COMMIT` on different pooled connections); the old seeder relied on `ON CONFLICT DO NOTHING`, which caught nothing because those tables have no unique constraint, so a second run duplicated every row. `db:seed` is the only entry point permitted to create the account; the scheduled refresh passes `create: false` and will not conjure its own target.

**The scheduled refresh is opt-in** (`DEMO_REFRESH_ENABLED=true`, every 30 days). The write itself lives in [backend/services/demoAccountService.ts](backend/services/demoAccountService.ts), shared by both callers so they cannot drift. It resolves the demo account by the **`is_demo`** column (migration `007`, unique partial index — at most one), never by email: `john.doe@example.com` is an ordinary address nothing reserves, and a timer pointed at a guessable string would wipe a real account's data monthly with nobody watching. Run by hand that exposure is bounded because a human is present; on a schedule it is not. The first `db:seed` after migration 007 adopts the existing demo row by setting the flag on it. The refresh throws rather than logging and returning, like `cleanupService`, and returns its **deleted** row count so `scheduleInterval` audits the destructive half per decision D.

Schema lives in [backend/db/schema.sql](backend/db/schema.sql) and is applied wholesale by `db:setup`, which is idempotent and safe to re-run. Tables: `users`, `transactions`, `savings_goals`, `import_batches`, `access_tokens`, `agent_conversations`, `agent_messages`, `agent_runs`, `agent_drafts`, `agent_receipts`, `agent_admissions`, `agent_goal_proposals` (`watchlist` and `ai_plans` were dropped by migration `014`; deploy code before applying it). Migration `015_agent_goal_proposals.sql` is recommended before deploying the planning backend, but not required: the store probes `to_regclass('agent_goal_proposals')` (caching only a positive answer, so applying 015 later needs no restart) and, while it is absent, conversations read with `goalProposal: null`, `propose_goal` answers `agent_unavailable`, the confirm/cancel routes answer 503 `agent_unavailable`, and the sweep skips the table. 015 is additive, idempotent, guarded for PostgreSQL 15 and refuses to run before `013`. `updated_at` is auto-maintained by triggers. `transactions.source` (migrations `011` and `013`) is `manual`, `ocr`, `ocr_llm`, or `agent`; `POST /transactions` and `PUT /transactions/:id` do not accept it. Import and agent confirmation set their own source. PostgreSQL 15+ is required for migration `013`'s column-specific `ON DELETE SET NULL`. Verify the migration on local/staging first; production application remains a separate operator action. `schema.sql` is the desired end state; incremental changes against an existing database go in [backend/db/migrations/](backend/db/migrations/) as numbered files, applied by hand with `psql -v ON_ERROR_STOP=1 -f`. Keep the three in step — the migration, `schema.sql` and [backend/types/db.ts](backend/types/db.ts), which holds one interface per table. A migration without the matching `schema.sql` edit means fresh setups and existing databases diverge; one without the matching `types/db.ts` edit means the row types describe a column that is no longer there, and nothing fails until a controller reads it.

**Connections**: `DATABASE_URL` points at Neon's *pooled* endpoint (`-pooler` in the host); the project lives in AWS `us-east-1`. The Render backend is in Oregon (us-west), not alongside it, so every query crosses the continent; moving either one is a separate decision. Every query in this codebase names tables unqualified, so [backend/db/connection.ts](backend/db/connection.ts) issues `SET search_path` on each new pool connection. This is defensive rather than load-bearing today — the AWS pooler hands out a normal `"$user", public` — but Neon's *Azure* pooler handed out an **empty** `search_path`, where every query failed with `relation "transactions" does not exist`. Keep it: it costs one statement per connection and makes the app behave identically on any endpoint. Don't move it into the pool's `options` — Neon's pooler rejects `search_path` as a startup parameter. Use the **direct** endpoint (drop `-pooler` from the host) for `pg_dump`/restore.

## Frontend architecture

- **Next.js 15 Pages Router** (`pages/`) with React 18. Add screens as files under `pages/`. Dependency security decisions and remaining advisories are recorded in [frontend/DEPENDENCIES.md](frontend/DEPENDENCIES.md).
- **API client**: [frontend/utils/api.ts](frontend/utils/api.ts) is a shared axios instance. A request interceptor attaches the JWT from `localStorage`; a response interceptor handles errors globally — `401` triggers `logout()`, and `403/404/500`/generic errors surface a SweetAlert2 dialog. `/auth/*` endpoints are exempted so components can handle those errors themselves. AI connections handles its own non-401 4xx errors from `/access-tokens`, and the agent caller handles `/agent` errors; a 401 still logs out. Import this instance rather than calling axios directly.
- **AI connections**: [frontend/components/AiConnections.tsx](frontend/components/AiConnections.tsx) is embedded in Settings. It lists token metadata and the deployment's MCP endpoint; a newly created secret lives only in component state and is discarded on dismissal or unmount, never put in localStorage.
- **Auth state** is `localStorage` `token` + `user`; there is no server session.
- **UI**: Radix primitives wrapped in [frontend/components/ui/](frontend/components/ui/) (shadcn-style), styled with Tailwind + `class-variance-authority`; use the `cn()` helper in [frontend/lib/utils.ts](frontend/lib/utils.ts) for conditional classes.
- **Transaction categories**: the canonical list is the exported `categories`
  object in [frontend/pages/transactions/new.tsx](frontend/pages/transactions/new.tsx)
  — the edit page and the dashboard both import it, and the dashboard uses it to
  decide whether a category is income or expense (unlisted names default to
  expense). Adding one means four edits, not one: that list, `CATEGORY_COLORS`
  in [frontend/pages/index.tsx](frontend/pages/index.tsx) (or it gets a
  hash-derived colour), and **both** `common.json` files, because the picker
  renders each name through `t(category)`. The manual transaction backend does not validate the
  category against any list; the agent path validates its canonical copy in `services/agent/validation.ts`, pinned by `agentValidation.test.ts`. The seed's copy in
  [backend/db/demoData.ts](backend/db/demoData.ts) is now pinned to this one by
  `test/demoData.test.ts`, which parses this file and compares. The locale
  files are still unguarded.
- **i18n**: `next-i18next` with `en` and `zh` locales in [frontend/public/locales/](frontend/public/locales/). Add user-facing strings to both `common.json` files.
- **Theme**: light/dark via [frontend/contexts/ThemeContext.tsx](frontend/contexts/ThemeContext.tsx).
- **On-device OCR**: [frontend/next.config.js](frontend/next.config.js) aliases `onnxruntime-web` to `frontend/lib/ocr/ortRuntime.js`, which loads the runtime with `importScripts` from `/ort/` instead of letting webpack bundle it — Next's minifier cannot parse the library's ESM build. Do not remove the alias. It runs single-threaded on purpose: multi-threaded WASM needs cross-origin isolation, and with isolation headers on, this classic-script runtime hangs starting its thread workers. Chrome throttles OCR to a crawl in a hidden or backgrounded tab; keep the tab visible while it runs.

## Environment

Both projects read `.env` (already present locally, gitignored). Backend needs `DATABASE_URL` (or `DB_*` parts), `JWT_SECRET`, and optionally email credentials and `MAILBOXLAYER_API_KEY`. Conversation recording adds `AGENT_ENABLED` (default false), `DEEPSEEK_API_KEY`, and `DEEPSEEK_MODEL` (default `deepseek-flash`); only set the flag after agent migration verification. Frontend needs `NEXT_PUBLIC_API_URL`. In production, DB connections use `ssl: { rejectUnauthorized: false }`.

Agent hosting requires a Node process able to spawn the SDK's platform-specific executable, its optional native package installed, writable temporary storage, outbound HTTPS to `https://api.deepseek.com/anthropic`, and an HTTP timeout longer than the 90-second model deadline plus cleanup. The pinned adapter has live local acceptance coverage; deployed Linux binaries, resource capacity and provider throttling require host verification. Do not silently enable this feature, migrate production or expose keys in diagnostics.

## Known gaps

Carried over from the improvement backlog, which is now retired — the reasoning
for anything already fixed lives in the comment next to the code, and the rest
is in git history.

- **Nothing guards the locale files against category drift.** Adding a
  transaction category means four edits (see above); `test/demoData.test.ts`
  pins the backend copy to the frontend list, but `check:locales` only warns
  about keys no locale answers, so a new category still ships untranslated.
- **`LOG_LEVEL` is close to inert** — it gates `logger.debug()` and nothing
  else. Setting it to `error` in production does not silence `info`; the
  `NODE_ENV` check already does that.
- **Retention settings do not persist.** `GET/PUT /transactions/retention-settings`
  reports a saved preference it never stores, and no scheduled job acts on one.
  The endpoint that does delete, `DELETE /transactions/auto-delete`, is
  validated but nothing in the UI calls it.
- **`/summary/rolling` serialises every transaction in the window twice** and
  aggregates in Node rather than SQL. That cost is per user and per request, so
  it is the gate on offering an *All time* period.
- **The frontend has no test runner**, so `lib/date.ts` is unguarded. Its
  backend twin, `utils/dates.ts`, is covered by `test/dates.test.ts`.
- **Phone OCR speed is unmeasured.** On a laptop (M-series Mac, Chrome,
  visible tab) screenshot import takes about 1–2 s per image; Chrome throttles
  a hidden tab to 8–15 s. A mid-range phone may be several times slower than
  either number — measure on a real device before announcing the feature.
- **The LLM fallback (spec §4.7) was not built.** The private set (seven real
  screenshots, 2026-09-17) is all read by the rule-based parser once each
  layout was added, so nothing yet shows it is needed. `POST /import/parse`
  reports `ai_fallback_unavailable` when the parser is unsure, and the import
  page falls back to showing the recognised text for manual entry. Build it
  only if `npm run benchmark -- --set private` on real screenshots shows a
  gap the parser itself can't close.
- **Uber and Uber Eats imports can double-count** a card charge already
  imported from a bank screenshot; `possible_duplicate` needs the same day,
  amount and currency, so a charge posted a day later is not flagged.
- **First screenshot-import use downloads about 45 MB** (the OCR model plus
  the ONNX runtime). The engine banner shows progress, and HTTP caching keeps
  it to once per browser.
